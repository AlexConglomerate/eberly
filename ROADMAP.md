# ebely — взгляд со стороны и план развития

Документ — честная оценка библиотеки и приоритизированный план, чтобы
она стала по-настоящему сильной. Не «всё классно», а где сильно, где
больно и куда не лезть. Архитектура подробно — в `ARCHITECTURE.md`.

---

## 1. Что мы делаем (кратко)

Конвейер: **схема API → типизированный клиент → им тестируем бэкенд.**

```
swagger/OpenAPI ──loadSpec──> spec
                 ──collectOperations──> Operation[]
                 ──renderClient──> текст файла (класс World)
                 ──writeFile──> generated.ts
```

- `World.createUser()` — изолированный «пользователь»: набор типизированных
  вызовов эндпоинтов + свежий `InternalStore`. Много пользователей =
  имитация разных людей; один пользователь с разными `headers` = разные
  устройства/сессии.
- Два режима, выбираются **на этапе генерации** (без рантайм-условий и
  conditional-типов):
  - `'test'` — метод → `ApiResponse` с `.status` / `.body` /
    `.assert(status, body?)`; не-2xx **не бросает**.
  - `'frontend'` — метод → тело напрямую; не-2xx бросает; `.assert` нет.
- `assert(status, body?)` — статус строго, тело **глубоко-частично**
  (сверяются только переданные поля).
- Цель на вход: разные источники схемы (старый Swagger 2.0, OpenAPI 3.x,
  позже TypeSpec; ещё дальше — gRPC/proto, AsyncAPI).

## 2. Что реально сильно (это не ломать)

1. **Узкая, честная задача.** «Сгенерировать типизированный клиент и
   тестировать им бэкенд» — это настоящая боль, и решение бьёт точно в неё.
2. **Решение про два режима без conditional-типов** (ARCHITECTURE §6) —
   зрелое. Большинство сделало бы это нечитаемыми дженериками. Это
   конкурентное преимущество, его надо **защищать**.
3. **`assert(200, { title })` с автокомплитом статуса + deep-partial тела** —
   это и есть killer-feature. В тестах почти никогда не нужно сверять
   тело целиком (id/таймстемпы плавают). Дефолт выбран правильно.
4. **Чистая архитектура.** Конвейер, чистые функции, один шаг = один файл,
   юнит-тесты без сети/IO. `ARCHITECTURE.md` документирован лучше, чем у
   большинства коммерческих библиотек.
5. **Модель `World` / `createUser` / `InternalStore`** хорошо ложится на
   реальные интеграционные сценарии: user A создал — user B прочитал;
   один юзер на двух устройствах; мульти-тенант.
6. **Детерминизм генерации** (байт-в-байт при повторе) — основа доверия к
   инструменту, который пишет код в репозиторий.

## 3. Слабые места и риски (честно, по убыванию боли)

| # | Проблема | Почему больно | Где |
|---|----------|---------------|-----|
| 1 | **Инлайн-типы вместо именованных.** `schemaToType` разворачивает `components/schemas` в структурный тип на каждом эндпоинте | На реальном API в `generated.ts` форма `Post` дублируется десятки раз: гигантский файл, нечитаемые ошибки TS, нельзя импортировать `Post` в хелпер, **бесконечная рекурсия на рекурсивных схемах** (`Comment.replies: Comment[]`) | `schema.ts`, `render.ts`, `operations.ts` |
| 2 | **Хрупкая группировка по `operationId`.** Нет точки — группа `default`, имя = весь id или `get/posts/{id}` | Обещание «прихожу в любой проект» ломается на первой же спеке без `operationId` с точкой (а таких большинство, особенно Swagger 2.0) | `operations.ts` |
| 3 | **Нет авторизации как first-class.** Только ручные `headers` | Для библиотеки тестирования бэкенда auth-флоу — сценарий №1. Нет «залогинься → возьми токен → подставляй Bearer» | `render.ts` + рантайм |
| 4 | **Бедное сообщение об ошибке.** `JSON.stringify` всего тела, без контекста запроса, по-русски | Для тест-либы сообщение о провале — это и есть продукт. Сейчас минимум | `response.ts` |
| 5 | **Только `application/json`.** Нет multipart/upload, бинарных ответов, form-urlencoded, `problem+json` | Тестировщики упираются в загрузку файлов постоянно | `schema.ts`, `operations.ts`, `render.ts` |
| 6 | **Нет рантайм-валидации ответа против схемы** | Типы *утверждают* форму тела, но никто не проверяет. Баг бэкенда (не та форма) = зелёный тест и враньё типов. Прямо мимо миссии «тестируем бэкенд» | новый слой |
| 7 | **Нет teardown/cleanup.** Тесты создают данные и не убирают | Загрязнение БД, порядко-зависимость, флаки | поверх интерцепторов |
| 8 | **Бедные матчеры.** Только равенство + deep-partial | Нет «поле существует / непустая строка / regex / длина массива / НЕ содержит `password`». Быстро упрёшься в ручные `if` | `response.ts` |
| 9 | **Swagger 2.0 не поддержан.** Код предполагает OpenAPI 3.x (`requestBody`, `components`) | Заявленная цель «старые свагеры» не выполняется; легаси-энтерпрайз весь на 2.0 | `operations.ts`, `schema.ts` |
| 10 | **Нет таймаута/abort/retry** в сгенерированном `request` | Зависший бэкенд вешает весь прогон тестов | `render.ts` |
| 11 | **Нет интеграции с тест-раннером.** Пример = `test1()` с `console.log` | Нет ненулевого exit-кода, отчётов, параллель-безопасности | пример + рецепты |
| 12 | **DX-трение для нович­ков.** Ручное копирование `swagger.json`, два импорта в сгенерированном файле, путь `configImport` | Бьёт сильнее всего по вайбкодерам и тестировщикам | конфиг + генерация |
| 13 | **Нейминг.** Пакет `ebely`, папка `evely`, ошибки по-русски | Для выхода к широкой аудитории нужен единый бренд + английский | весь репозиторий |

## 4. Аудитории: кому что нужно и насколько мы подходим

| Аудитория | Подходим? | Что любят | Что блокирует сейчас |
|-----------|-----------|-----------|----------------------|
| **Проф. разработчики** (бэк/фуллстек) | **Сильно** | Типизированный клиент из схемы, deep-partial assert, мульти-юзер, один клиент и для тестов и для фронта (`frontend` режим — реально снижает дрейф) | Инлайн-типы, нет именованных моделей, нет auth-хелпера, OpenAPI-3-only. Сравнивают с `openapi-typescript`+`openapi-fetch`, `orval`, `kubb`, `hey-api` — **отстраиваться надо эргономикой тестирования, не генерацией клиента** (это переполненная ниша) |
| **Тестировщики / QA** | **Большой потенциал, сейчас слабее всего** | Мульти-юзер модель = моделировать пути пользователя; читаемые проверки; фикстуры; отчёты | Бедные матчеры, нет фикстур/фабрик, нет отчётов (JUnit/HTML), ошибки TS-тяжёлые и по-русски. **Мало кто из типизированных инструментов любит тестировщиков — тут можно стать №1** |
| **Вайбкодеры** (AI-assisted) | **Сильный потенциал, низкая полировка** | «Указал свагер → готовый клиент → `.assert(200, {...})`» очень LLM-/copy-paste-дружелюбно | Двойной импорт-конфиг и ручной `swagger.json`. Нужен zero-config, одна команда, авто-пример теста, MCP-сервер / Claude skill, рецепты в README |
| **Хайлоад / перф-команды** | **Слабее всего — честно не ваша ниша** | Нагрузка, параллелизм, таймауты, детерминированный teardown, CI/контрактные тесты | Это инструмент функциональной корректности, **не k6/Gatling**. Реальная ценность тут — контрактные/интеграционные тесты в CI и лёгкий «N параллельных юзеров» поверх мульти-юзер модели. Не вкладываться в погоню за этой аудиторией |

**Вывод:** целиться в **проф-разработчиков + тестировщиков** (интеграционные/
контрактные тесты), вайбкодеров использовать как **канал дистрибуции**
(DX и AI-дружелюбность). Хайлоад и мульти-протокол — не сейчас.

## 5. План по приоритетам

### P0 — без этого нельзя выходить к людям

1. **Именованные типы из `components/schemas`.** Эмитить
   `export interface Post {...}` и ссылаться по имени. Решает разом:
   размер файла, читаемость ошибок, **рекурсивные схемы**,
   переиспользование типов в хелперах. — `schema.ts` (резолв → имя типа),
   `render.ts` (блок объявлений типов), `operations.ts`.
2. **Устойчивость к реальным спекам.** Группировка по OpenAPI `tags`
   (стандарт) с фолбэком; санитизация и дедуп имён методов; рекурсивные
   `$ref` без зацикливания; ответы без `application/json`; пустые тела;
   `default`-ответ. — `operations.ts`, `schema.ts`.
3. **Авторизация first-class.** Хелпер «логин → захват токена → авто-Bearer
   на последующие запросы этого юзера», завязанный на `createUser` /
   `InternalStore`. Это сценарий №1 для тестирования бэкенда.
4. **Сообщение об ошибке assert.** Контекст запроса (метод + URL +
   отправленное тело), путь расхождения с подсветкой/диффом, обрезка
   больших тел, **английский** (или i18n). — `response.ts`.
5. **Интеграция с тест-раннером.** Рецепты/адаптеры для `node:test` и
   `vitest`; ненулевой exit-код при провале; параллель-безопасные юзеры.

### P1 — то, за что полюбят

6. **Интерцепторы** (request/response хуки). Сценарии: подстановка токена,
   логирование, корреляция, запись созданных сущностей. *Дизайн —* см. §7.
7. **Авто-cleanup / teardown.** Реестр созданных ресурсов (поверх
   интерцепторов + `InternalStore`, естественно ложится на уже имеющийся
   `createdPosts`) → авто-удаление в конце.
8. **Рантайм-валидация ответа против схемы** (опц. режим). Схема уже под
   рукой на этапе генерации. Ловит враньё типов — прямо по миссии.
9. **Богаче матчеры — как escape hatch, НЕ Jest-клон.** Предикат-функция /
   `expect.any`-подобное / «поле существует» / regex / длина массива /
   негатив. Deep-partial остаётся дефолтом.
10. **Zero-config DX.** Убрать ручное копирование `swagger.json`
    (брать по `url`/из `your-app` напрямую), авто-вывод `configImport`,
    одна команда, генерация примера теста из спеки.
11. **multipart/upload, бинарные ответы, content-type негоциация.**
12. **Swagger 2.0** через конвертер 2.0→3.0 (не руками в каждом месте);
    **TypeSpec** как input-адаптер (`tsp compile` → OpenAPI → тот же конвейер).
13. **Таймаут/abort/retry** в сгенерированном `request`.

### P2 — ширина (явно отложить; гейт = HTTP-ядро отполировано)

14. **gRPC/proto** — отдельный пакет, общий core (assert/store/мульти-юзер).
15. **AsyncAPI (WS/Kafka/Rabbit)** — это **другой продукт**: модель
    «запрос→ответ→assert» не ложится на pub/sub (проверяешь *со временем
    полученные сообщения*, порядок, топики, consumer groups). Отдельный
    пакет, разговор уровня «v2 или никогда».

## 6. Что тестировать

- **Корпус реальных спек** как golden/snapshot для `renderClient`
  (он детерминирован — это уже ценность): Petstore v2 и v3, спеки с
  рекурсией, с `tags` без `operationId`, `allOf`/`oneOf`/`anyOf`,
  `nullable`, `enum`, без 2xx-ответа, с multipart, большие реальные
  (GitHub/Stripe-подобные).
- **Юнит чистых функций** (есть `response.test.ts`, `render.test.ts`)
  расширить: рекурсивный `$ref`, отсутствующая схема, не-JSON тело,
  коллизии имён методов, пустое тело, `default`-ответ.
- **Тип-уровневые тесты** (`tsd` / `expectTypeOf`): `assert(201)` при
  только `200` — ошибка типов; `body` сужается по статусу; `DeepPartial`
  не пропускает лишние поля.
- **E2E:** поднять `your-app`, прогнать сгенерированный клиент в обоих
  режимах против живого бэкенда.
- **Регресс детерминизма:** повторная генерация = байт-в-байт (CI-гейт).

## 7. Чего НЕ делать (дисциплина скоупа — самое важное)

- **Не уходить в мульти-протокол** (Kafka/gRPC/AsyncAPI), пока HTTP-ядро
  не отполировано. Ширина соблазнительна — именно так умирают хорошие
  библиотеки. **Глубина > ширина.**
- **Не превращать `assert` в Jest/Chai.** Deep-partial-дефолт — это
  дифференциатор; матчеры — тонкий escape hatch, а не DSL.
- **Не вводить рантайм-условия/conditional-типы по режиму** — защищать
  решение из ARCHITECTURE §6.
- **Не гнаться за перф/хайлоад-аудиторией** — честно не ваша ниша; быть
  k6 «тоже» = размыть продукт.
- **Не плодить опции конфига.** Каждая опция — налог на пользователя и на
  поддержку. Лучше один хороший дефолт, чем флаг.
- **Интерцепторы — спроектировать узко:** фиксированные точки
  (`onRequest` / `onResponse`), синхронный/async, без права переписать
  весь движок. Это не плагин-фреймворк, а 2–3 хука.

---

## 8. Как стать легендарной

1. **Продукт — это сообщение об ошибке и онбординг за 2 минуты.** Не
   количество фич. Вкладываться сюда непропорционально.
2. **«Работает на любом свагере» важнее новых фич.** Один креш на
   рекурсивной схеме теряет доверие навсегда; «съел любой свагер,
   что я кинул» — зарабатывает его.
3. **Один killer-feature держать острым:** deep-partial assert +
   мульти-юзер модель. Всё остальное строится вокруг, не вместо.
4. **Детерминизм генерации + корпус-снапшоты = доверие** к коду, который
   мы пишем в чужой репозиторий.
5. **Выбрать аудиторию и не распыляться:** проф-разработчики +
   тестировщики; вайбкодеры — канал (DX, MCP/Claude skill, рецепты).
6. **Сначала закончить HTTP-историю, потом протоколы.** P2 — это
   разговор после того, как P0+P1 сделаны и любимы.
